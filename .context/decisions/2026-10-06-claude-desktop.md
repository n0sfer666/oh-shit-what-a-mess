# ADR: очистка Claude Desktop

Дата: 2026-10-06
Статус: принято (решения пользователя через интервью)

## Контекст

`~/Library/Application Support/Claude` весил 13.3 GB и целиком был `InfoOnly/Danger` вместе
с `Claude/vm_bundles` — один и тот же объём показывался дважды, а удалить ничего было нельзя.
Состав: базовый образ Cowork-VM `rootfs.img` (~10 GiB, рядом `.rootfs.img.origin`-хеш),
`sessiondata.img` (сессии Cowork), Chromium-кэши (~1.5 GB), встроенные сборки Claude Code по
версиям (~220 MB каждая, старые не удаляются самим Claude).

## Решение

- Отдельная категория `claude`; все цели `Caution` и блокируются, пока запущен процесс `Claude`
  (`Target.blocking_app`, детект через тот же `lsof`).
- `rootfs.img` — осознанное исключение из правила 6: это скачиваемый артефакт, а не контейнер
  состояния. Удаляется только вместе с `.rootfs.img.origin` (образ + манифест), только при
  закрытом Claude. Исключение перечислено поимённо в `registry/tests/invariants.rs`.
- `sessiondata.img` и сам `claudevm.bundle` целями не бывают.
- Кэши — тот же набор `CACHE_DIRS`, что у браузеров, риск как у браузеров.
- Сборки Claude Code — поштучно, пользователь выбирает версию сам.

## Последствия

- Повторная загрузка образа Claude'ом при следующем Cowork из кода не наблюдаема — проверяется
  вручную по `.context/testing.md` («Ручная проверка: Claude Desktop»).
- Блокировка проверяется дважды: при скане и прямо перед удалением (`blocking::Recheck`).
  Сбой `lsof` трактуется как «Claude, возможно, запущен» — цели блокируются.
- Рядом с образом лежат `.cowork-adopted` и `.{vmlinuz,initrd,initrd-micro}.origin` с тем же
  хешем, а также пустые `vm_bundles/warm/<hash>/`. Они не удаляются: решение пользователя —
  только `rootfs.img` (+ его `.origin`). Как Claude поведёт себя при живом `.cowork-adopted`
  без образа — из кода не наблюдаемо, проверяется шагом 3 runbook.
